# meal-nutrition

餐食照片营养分析。固定输出模板，保证每天记录字段一致，便于长期趋势分析。

## 触发场景

- 用户发来一张餐食照片（早餐 / 午餐 / 晚餐 / 加餐）

## 分析流程

1. 识别食物种类与大致分量。参考常见餐盘、手掌做分量估计（如一份掌心大小的肉类约 100g）。
2. 估算总热量与三大营养素。
3. 估算膳食纤维与钠（若可从照片判断）。
4. 计算均衡分（0-10）与针对目标的点评。
5. 按 schema 组装 `metrics` 并写入 `domains/health/data/meals/<YYYY-MM>.json`。

## 晨间固定流程（优先套用）

用户工作日晨间固定：骑行后等班车时吃**半截香蕉**（加餐，≈45 kcal / 碳水 11.5 g），训练结束后吃**练后第一餐**。完整流程与推定规则见 [`domains/health/reference/morning_routine.md`](../domains/health/reference/morning_routine.md)（生效 2025-10-20）。

## 食堂餐食的估算口径

餐食来自**已入库食堂**（食堂名由使用者自建数据）时，先查 `domains/health/canteen/`：

- `dishes/<食堂>.json` —— 菜品库，含 `category`、`protein_source`、`oil_level`、`nutrition_ref_key`、`pricing_mode`
- `nutrition_ref.json` —— 分类默认营养值、烹饪用油系数、每日目标线

**优先用菜品库的 `nutrition_ref_key` 查参考表取基准值，再按 `oil_level` 与用户实际吃法（去皮 / 沥汁 / 剩菜 / 汤喝没喝）调整**。不要脱离参考表凭空估。

用户明确说了吃法细节时按下表调整，这是食堂估算里误差最大的部分：

| 用户说法 | 调整 |
| --- | --- |
| 去皮吃 | 扣皮的脂肪与热量（鸡腿去皮约 −40kcal / −3.5g 脂肪） |
| 汤汁 / 卤汁未喝 | 钠下调（约 −300~600mg），脂肪略降 |
| 只吃躯干 / 去头尾 | 按净肉重重估，通常比带骨带壳低 30–40% |
| 有剩（如"青椒没吃完"） | 扣掉剩余部分**及其吸附的油汁**（油是主要来源，别只扣菜本身） |

## 份量修正链（用户事后更正份量时的处理）

用户对已记录的餐食更正份量时（如「面包不是 4 片是 1/4 片」「三明治没有酱料」）：

1. **原地更新**该条记录，不新增、不删除，并打 `updated_at`。
2. 在 `note` 里**保留完整修正链**（如「600 → 250（面包/荷包蛋改 1/4 份）→ 244（去酱料）」），便于追溯每次改了什么。
3. 重算后**主动复核画像是否反转**——份量大幅下调后，原本"脂肪超标"可能变成"蛋白不足、总量偏小"，点评要跟着改，不能只改数字不改结论。
4. 刷新看板：`python3 scripts/normalize_health_data.py`。

## 待确认项的处理

照片看不清或存在多种可能时（面包片数、酱料有无、是否喝汤、份量是否吃完），**按最合理假设估算并落库，同时在 `note` 末尾用「**待确认**：…」列出假设**。不要为了回避假设而不记录，也不要把假设当成事实写进 `comment`。

用户确认或否认后，按上面的修正链流程更新。

## 凭证（小票 / 订单截图）的使用口径

用户补发电子小票、订单截图、外卖单时，**凭证只能用来确认"规格"，不能用来确认"时间"**：

| 凭证字段 | 怎么用 |
| --- | --- |
| 规格（杯型、糖度、冰量、加料、备注） | **采信**，用来坐实 `note` 里的待确认项并重算（如「3分糖」→ 糖按 30% 计） |
| 门店 / 产品名 / 配料 | **采信**，用于校准品类与分量 |
| 打印时间 / 下单时间 | **不采信时间**——小票机系统时间常未校准，也可能是补打或旧凭证 |

- 时间一律以**用户口述或消息发送时刻**为准（默认取用户发图时刻，可修正）。
- 若凭证时间与记录时间冲突，**不要自行改日期**，直接在 `note` 里标注差异并**问用户**；用户确认后按回复处理，并把「时间以用户口述为准」的结论写进 `note`。
- 订正后要复核结论是否变化：例如减糖只降热量但脂肪未动时，脂肪供能比反而**上升**，点评必须重写，不能只改数字。

## 多容器 / 多盒餐食的拆分口径

外卖食盒、分格餐盒、一单多盒（如「主食盒 + 蔬菜盒」）时，**按容器拆成多条记录，不合并成一条**：

- 每条对应一个容器，`meal_slot` 相同、`time` 相同，`note` 里互相注明「本条 = XX 盒，另一条 = YY 盒」。
- 好处是后续核对时可单独订正其中一盒（如「蔬菜盒其实淋了油醋汁」只需改一条），合并成一条就得整条重算。
- 蛋白、碳水、纤维分别归属到实际所在的那盒，不要平摊。
- 拆分后 `balance_score` **各盒独立评分**（如主食/蛋白盒与蔬菜盒都可以是 9 分），不要为了"总餐分"硬拉平均。

## 奶制品与含糖饮料的记录口径

- **牛奶 / 豆浆 / 酸奶有标签时按标签取值**，在 `comment` 注明「按标签取值，非估算」，与估算值严格区分。
- 换算公式：`每100ml 值 × 体积(ml) ÷ 100`；能量若给的是 **kJ，需 ÷4.184 换成 kcal**（易错点）。
- **算食物含水，记入 meal，不重复计入饮水**（`water-log` 不加这一笔）。
- 有标签的奶制品要**顺手记钙、饱和脂肪**：例如全脂奶 3.8g 脂肪/100ml 中约 2.5g 为饱和脂肪，控脂期应优先选低脂/脱脂。

## 对用户（薄肌增肌减脂）的点评规则

用户目标是"薄肌"，即在低体脂前提下保有清晰肌肉线条。点评围绕：

- 蛋白质：单餐是否达到约 30g 以上，全天是否集中在合理分布
- 碳水：是否以复杂碳水为主，精制糖是否偏多
- 脂肪：是否过量，来源是否健康
- 热量：是否与当日目标匹配，避免单餐过高

点评语气客观，只做营养结构分析，不下医学结论。

## 用户向回报格式

向用户回报时用简洁表格，不要抛原始 JSON：

```
早餐已记录 · 520 kcal · 均衡分 8/10
蛋白 32g / 碳水 60g / 脂肪 14g
点评：蛋白质达标，碳水以全麦为主，脂肪略高，可减少煎蛋用油。
```

## 注意事项

- 照片不清或无法识别食物时，向用户确认，不要编造热量。
- 分量估算需说明是估算值（±25%–30%），允许用户手动修正。
- 同一天多餐分别记录，以 `meal_slot` 区分；加餐记 `snack`，补剂（蛋白粉 / 肌酸）也记 `snack`。
- **补剂类**（蛋白粉、肌酸软糖、咖啡）按产品营养标签取值时，在 `comment` 里注明"按标签取值，非估算"，与估算值区分开。
- 饮品（白水、茶、咖啡）**不记入 meal**，走 `water-log`；牛奶、豆浆、汤、粥算食物含水，记入 meal 但不重复计入饮水。
- 记录后跑 `python3 scripts/normalize_health_data.py` 刷新看板。
